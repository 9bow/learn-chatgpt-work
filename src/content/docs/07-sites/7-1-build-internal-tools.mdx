## 문서로는 끝나지 않는 일이 있다

출시 준비 상황을 정리해 달라는 요청을 받았다. 마일스톤은 스프레드시트에, 담당자는
슬랙 스레드에, 리스크는 지난주 회의록에 있다. 문서 한 개로 정리해 공유하면 이틀 뒤에
다시 낡는다. 매주 회의 전에 같은 작업을 반복하게 되고, 팀원들은 "최신 버전이 어디
있나요"를 계속 묻는다.

이럴 때 필요한 것은 더 잘 쓴 문서가 아니라 **팀이 다시 찾아올 한 페이지**다. Sites는
바로 이 지점을 겨냥한 기능이다. OpenAI Academy의 표현을 빌리면, 사이트는 "할 일이
머물 자리가 필요할 때" 쓸모가 있다. 출시 트래커, 주간 리뷰용 대시보드, 선택지를
따져 보는 계산기, 새 프로젝트 합류자를 위한 온보딩 페이지가 그런 예다.

## Sites가 하는 일

공식 주간 업데이트 문서는 Sites를 이렇게 소개한다. **Sites는 ChatGPT가 웹사이트,
대시보드, 내부 도구, 웹 앱, 게임을 만들고(create) 저장하고(save) 배포하고(deploy)
살펴보게(inspect) 해 주며, 이 결과물은 OpenAI가 호스팅한다.** 별도의 배포 스택을
꾸리지 않고도 프롬프트나 기존 프로젝트를 호스팅되는 결과물로 바꿀 수 있다는 것이
핵심이다. 호스팅, 접근 제어, 스토리지, 데이터베이스 지원이 함께 들어 있다.

Sites는 **2026년 6월 1~5일 주차**에 공개됐고, ChatGPT 웹과 데스크톱 앱에 전용
진입점이 있다. 웹에서는 **More**에서 **Sites** 를 고르거나 사이트 목록 페이지로
바로 들어가고, 데스크톱 앱에서는 **Sites** 를 열어 만든 사이트를 다시 열고 관리한다.

Sites는 **퍼블릭 베타**다. 가용성은 플랜·지역·워크스페이스 설정에 따라 다르고, 베타
기간에는 모든 사이트에 플랜별 사용량 한도가 적용된다. ChatGPT가 현재 한도를 보여
주고 한도에 가까워지면 알려 준다. 한도에 도달하면 새 사이트 생성, 스토리지 추가,
사용량이 많은 사이트의 공개 유지가 막힐 수 있지만, 이미 있는 사이트를 편집하고
관리하는 것은 계속 할 수 있다. 이 사이트에서 다루는 다른 기능과 마찬가지로 기능은
플랜, 플랫폼, 지역, 롤아웃, 워크스페이스 설정에 따라 달라진다.

## 문서 · 내부 사이트 · 경량 앱 · 소프트웨어 프로젝트

Sites를 잘 쓰는 첫걸음은 "이건 사이트로 만들 일이 아니다"를 알아보는 것이다. Academy
페이지는 네 가지 형식을 구분한다.

| 형식 | 어떤 때 쓸모가 있나 | 예시 |
|---|---|---|
| 문서(document) | 정보를 읽거나 공유할 때 | 글로 쓴 출시 계획 |
| 내부 사이트(internal site) | 여러 사람이 다시 찾아올 한 페이지가 필요할 때 | 마일스톤과 링크가 담긴 출시 트래커 |
| 경량 앱(lightweight app) | 사람들이 정보를 직접 다루도록 돕고 싶을 때 | 프로젝트 선택지를 비교하는 계산기 |
| 큰 소프트웨어 프로젝트 | 더 복잡하거나 장기적인 제품 요구를 지원할 때 | 고급 인프라 요구가 있는 맞춤 시스템 |

**내부 사이트** 는 조직이나 워크스페이스 안의 사람들을 위해 만든 웹페이지다. 특정
업무에 대해 팀이 돌아올 한 곳을 준다. 예를 들어 제품 출시의 마일스톤, 담당자, 링크,
리스크를 한데 모아 두면 팀원들은 여러 문서를 뒤지는 대신 한 페이지를 열어 최신 정보를
확인한다.

**경량 앱** 은 여기에 상호작용이 더해진 것이다. 계산기는 몇 가지 입력을 받아 결과를
보여 주고, 대시보드는 일정한 형식으로 정보를 검토하게 돕는다. 이런 도구는 완성된
소프트웨어 제품보다 범위가 작고, 보통 한 팀·한 프로젝트·하나의 반복 워크플로를 위해
만든다. Academy 페이지도 "쓸 만한 사이트는 작아도 된다"고 못 박는다. 목표는 사람들이
열어서 특정 작업에 쓸 수 있는 무언가를 만드는 것이다.

## 좋은 첫 사례 고르기

좋은 첫 사이트는 **정해진 사람들에게 명확한 문제 하나**를 풀어 준다. Academy 페이지가
제시한 조합은 다음과 같다.

| 팀에 필요한 것 | 만들 수 있는 것 | 담을 내용 |
|---|---|---|
| 출시 상황 추적 | 출시 트래커 | 마일스톤, 담당자, 링크, 리스크 |
| 매주 정보 검토 | 대시보드 | 리뷰 미팅에서 실제로 쓰는 정보 |
| 선택지 비교 | 계산기 | 입력값, 가정, 명확한 결과 |
| 새 사람의 프로젝트 합류 | 온보딩 페이지 | 배경, 참고 자료, 다음 단계 |
| 프로젝트 정리 | 내부 페이지 | 핵심 링크, 업데이트, 참고 자료 |

여기에 하나 더 정해 두면 좋은 것이 **저장이 필요한지**다. 공식 문서는 필요한 제품
동작을 미리 알려 주면 Sites가 적절한 사이트 형태를 고른다고 안내한다.

| 사이트에 필요한 것 | Sites에 요청할 것 |
|---|---|
| 콘텐츠 중심 웹사이트나 랜딩 페이지 | 꼭 필요하지 않다면 영구 저장 상태 없이 |
| 저장되는 기록, 사용자 진행 상황, 게임 점수 | 구조화 데이터용 관계형 데이터베이스(D1) |
| 이미지·문서·오디오·비디오 등 업로드 파일 | 파일용 오브젝트 스토리지(R2) |
| 검색 가능한 메타데이터가 있는 업로드 파일 | 메타데이터는 D1, 파일 내용은 R2 |
| 현재 워크스페이스 사용자 신원이 필요한 내부 사이트 | 워크스페이스 인증 사용자 신원 |
| 공개 로그인이나 외부 ID 공급자 | 인증이 활성화된 사이트 |

주의할 구분이 있다. 테마 선택이나 닫은 배너처럼 **일시적인 표시 상태** 에는 영구 저장을
요청하지 않는다. 반대로 호스팅된 사이트가 기억해 주기를 사람들이 기대하는 **제품
데이터** 에는 요청한다.

## 만드는 흐름: 설명 → 검토 → 수정 → 공유

공식 문서가 정리한 Sites 워크플로는 네 단계다.

```text
┌─────────────────┐
│ 1. 설명하기     │ 대상 · 목적 · 필요한 동작 · 사용할 정보
└────────┬────────┘
         ▼
┌─────────────────┐
│ 2. 검토하기     │ 의도한 정보를 썼는가 · 데이터를 어떻게 다루는가
└────────┬────────┘
         ▼
┌─────────────────┐
│ 3. 다듬기       │ 바꿀 점을 말로 설명 · 필요하면 파일·화면 첨부
└────────┬────────┘
         ▼
┌─────────────────┐
│ 4. 관리와 공유  │ 다시 열어 수정 · 방문 대상 선택 · 링크 공유
└─────────────────┘
         │
         └─▶ 내용이 바뀌면 3번으로 돌아간다
```

**1단계** 에서는 누가 쓸지, 무엇을 위한 페이지인지, 어떤 동작이 필요한지, 어떤 정보를
써야 하는지를 함께 준다. **2단계** 에서는 생성된 내용과 동작을 검토한다. 여기서 볼
것은 디자인이 아니라 "의도한 정보를 썼는가"와 "데이터를 예상대로 다루는가"다.
**3단계** 에서는 바꿀 점을 말로 설명한다. 화면 캡처나 파일을 함께 주면 수정이 빨라진다.
**4단계** 에서는 Sites로 돌아가 사이트를 다시 열고 다듬고, 준비되면 방문 대상을 정해
링크를 공유한다.

Sites 워크플로를 명시적으로 시작하려면 공식 안내대로 프롬프트에 "website"라는 단어를
넣거나 `@Sites` 를 멘션한다. 한국어로 요청할 때는 `@Sites` 를 함께 적어 두면 의도가
분명해진다.

## 해보기

**첫 사이트: 출시 트래커**

```text
@Sites 우리 크로스펑셔널 팀이 쓸 출시 트래커 웹사이트를 만들어 주세요.
마일스톤, 담당자, 링크, 리스크, 주간 업데이트 섹션을 포함해 주세요.
주간 리뷰 회의에서 훑어보기 쉬운 구조로 만들어 주세요.
만들기 전에 간단한 페이지 구조를 먼저 제안하고, 필요한 정보를 저에게 질문해 주세요.
```

**경량 앱: 선택지 비교 계산기**

```text
@Sites 우리 팀이 프로젝트 선택지를 비교할 수 있는 경량 웹 앱을 만들어 주세요.
먼저 입력값, 가정, 점수 규칙을 저에게 물어봐 주세요.
그다음 점수가 어떻게 계산됐는지 보여 주는 결과 페이지를 만들어 주세요.
```

**저장이 필요한 사이트: 요청 대시보드**

```text
@Sites 운영팀용 프로젝트 요청 대시보드 웹사이트를 만들어 주세요.
팀원이 요청을 등록하고, 각 요청의 담당자를 확인하고, 상태를 갱신하고,
목록을 필터링할 수 있게 해 주세요.
워크스페이스 계정으로 로그인하게 하고, 요청 데이터는 방문 사이에 저장해 주세요.
```

**검토 먼저, 배포는 승인 후**

```text
@Sites 이 프로젝트로 반응형 출시 대시보드를 만들어 주세요.
모바일과 데스크톱 크기에서 검증하고, 검토용 버전을 저장해 주세요.
제가 저장된 버전을 승인하기 전까지는 배포하지 마세요.
```

마지막 프롬프트는 공식 문서가 예시로 제시한 패턴이다. **배포 URL은 모두 프로덕션
배포** 이므로, 라이브로 만들기 전에 확인하고 싶다면 배포 없이 버전만 저장하도록
요청한다. 다음 챕터에서 이 두 단계를 자세히 다룬다.

## 주의점과 한계

| 하기 쉬운 실수 | 대신 이렇게 |
|---|---|
| "회사 홈페이지를 만들어 주세요"처럼 범위를 넓게 잡는다 | 한 팀·한 워크플로를 위한 작은 페이지 하나로 시작한다 |
| 대상과 목적을 말하지 않고 만들라고 한다 | 누가 쓰는지, 무엇을 하려는지, 어떤 정보를 쓸지 먼저 적는다 |
| 일시적 표시 상태에도 저장을 요청한다 | 사람들이 기억되길 기대하는 제품 데이터에만 저장을 요청한다 |
| 만들자마자 링크를 공유한다 | 내용·데이터 처리·대상을 검토한 뒤 공유한다 |
| 사이트가 사내 데이터와 실시간으로 연결될 것이라 기대한다 | 현재는 라이브 데이터 직결이 안 된다. 7-2에서 다루는 예약 작업 패턴을 쓴다 |

지원되지 않는 용도도 문서에 명시돼 있다. Sites는 지원되는 런타임에서 동작하는 웹
경험을 호스팅하며, 일부 프레임워크·사설 네트워크·데이터베이스·백그라운드 서비스·호스팅
패턴은 지원되지 않는다. 출시 시점 기준으로 **데이터 레지던시와 추론 레지던시를
지원하지 않는다.** 배포된 사이트, 사이트 코드, D1·R2 데이터와 파일 저장, 생성된
산출물, 로그가 모두 여기에 해당한다. 또한 보호 대상 건강정보(PHI)나 결제카드 데이터를
처리하는 용도, 13세 미만(또는 해당 지역의 디지털 동의 연령 미만)을 대상으로 하는
용도, 금융 거래를 가능하게 하는 용도, 악성코드 배포, 피싱, 사람이나 조직 사칭에는
쓸 수 없다.

Enterprise 워크스페이스에서는 **관리자가 ChatGPT Sites의 사용 가능 여부 자체를
제어** 한다. 화면에 Sites가 보이지 않으면 대개 플랜·지역·워크스페이스 설정 문제다.

## 정리

- Sites는 ChatGPT가 웹사이트·대시보드·내부 도구·웹 앱·게임을 만들고 저장하고 배포하고
  살펴보게 해 주는 기능이며, 결과물은 OpenAI가 호스팅한다. 2026년 6월 1~5일 주차 공개,
  현재 퍼블릭 베타다.
- 같은 요구를 문서로 풀 수도 있다. 여러 사람이 다시 찾아올 한 페이지가 필요할 때
  내부 사이트, 사람들이 정보를 직접 다뤄야 할 때 경량 앱을 고른다.
- 좋은 첫 사이트는 정해진 사람들에게 명확한 문제 하나를 푼다. 출시 트래커, 주간 리뷰
  대시보드, 선택지 계산기, 온보딩 페이지가 대표적이다.
- 저장이 필요한지 미리 말해 준다. 일시적 표시 상태에는 저장을 요청하지 않는다.
- 설명 → 검토 → 수정 → 관리와 공유 루프로 다듬는다. 배포 URL은 모두 프로덕션이므로
  검토 전에는 버전만 저장하게 한다.

다음 챕터에서는 버전 저장과 배포의 차이, 공유 대상을 정하는 방법, 그리고 라이브
데이터에 직접 연결할 수 없는 사이트를 어떻게 최신 상태로 유지하는지를 다룬다.
