## 배포는 되돌리기 어려운 행동이다

사이트를 만드는 것보다 어려운 일은 "언제 누구에게 보여 줄지" 정하는 것이다. 공식
문서의 경고는 짧고 분명하다. **Sites의 배포 URL은 모두 프로덕션 배포다.** 라이브가
되기 전에 결과를 보고 싶다면, 배포하지 말고 버전만 저장하라고 요청해야 한다.

한 번 사내 전체에 링크를 뿌린 뒤 "아, 이 표에 아직 확정 안 된 인건비가 들어 있었네"를
발견하는 상황을 피하려면, 만들기와 공개를 별개의 단계로 다루는 습관이 필요하다.

## 버전 저장과 배포는 다른 단계다

공식 문서는 Sites의 게시를 두 단계로 나눈다.

1. **버전 저장(save a version).** ChatGPT가 배포 가능한 버전을 빌드한다. 로컬 소스
   프로젝트에서 만든 사이트라면 빌드에 쓰인 Git 커밋과 버전을 연결한다. 검토할 수
   있는 배포 후보가 필요할 때 이 단계를 쓴다.
2. **버전 배포(deploy a version).** 저장된 버전을 게시하고, 배포가 성공하면 프로덕션
   URL을 알려 준다. 선택한 대상이 사이트에 접근하기를 의도할 때만 이 단계로 넘어간다.

저장된 버전이 여러 개 있을 때는 목록을 보여 달라거나 특정 버전을 살펴봐 달라고
요청해 이전 배포 후보를 찾을 수 있다. 이 버전 목록과 검사는 데스크톱 앱을 기준으로
문서에 설명돼 있다.

```text
┌──────────────────────┐
│ 사이트 만들기 / 수정 │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 1) 버전 저장 (save)  │ ─▶ 배포되지 않은 검토용 후보
└──────────┬───────────┘
           │  내용 · 데이터 처리 · 대상 검토
           ▼
┌──────────────────────┐
│ 2) 버전 배포 (deploy)│ ─▶ 프로덕션 URL이 나온다
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 3) 접근 대상 설정    │ ─▶ 가장 좁은 범위부터
└──────────────────────┘
```

배포가 끝나면 URL이 나온다. 자동으로 배포되지 않았다면 배포해 달라고 직접 요청하면
된다. 여기서 Academy 페이지가 짚는 실무 주의사항이 하나 있다. **배포된 링크는
Chrome에서 열어 한 번 더 확인한 다음 공유한다.** 7-1에서 본 작업 중 미리보기와 달리,
배포된 사이트 확인에는 내장 브라우저(in-app browser)가 현재 지원되지 않는다.

## 공유 전 검토: 내용과 대상을 모두 본다

사이트에는 계획, 분석, 프로젝트 정보, 사용자가 입력한 내용이 들어 있을 수 있다.
Academy 페이지의 표현대로 **내용과 대상을 모두** 확인해야 한다. 공식 문서의 검토
항목은 다음과 같다.

- 내용을 검토한다. 생성된 텍스트와 이미지, 링크, 업로드한 파일, 폼, 상호작용 동작까지.
- 기밀 정보나 민감 정보, 비밀 값, 공유 권한이 없는 제3자 콘텐츠가 노출되지 않는지 확인한다.
- 의도한 방문자 경험으로 사이트를 테스트한다. 접근 설정과 로그인 동작까지 포함해서.
- 개인정보나 방문자 입력을 수집하는 기능을 검토한다. 그 정보를 수집·공유·게시할지 결정한다.
- Sign in with ChatGPT를 쓴다면, 사이트가 어떤 방문자 정보를 받고 어떻게 쓰는지 설명한다.
- 개인정보를 수집하거나 처리한다면 관련 개인정보·데이터 보호 법령을 준수한다.
- 의도한 대상에 맞는 **가장 좁은 공유 옵션** 을 고른다.
- 공유한 사이트를 직접 열어 의도한 대상이 방문할 수 있는지 확인한다.

## 접근 범위 정하기

새로 만든 사이트는 접근을 바꾸기 전까지 **소유자와 워크스페이스 관리자에게만**
제한된다. 내용, 데이터 처리, 예상 대상을 검토하는 동안에는 이 상태를 유지하는 것이
좋다. 계정과 워크스페이스 설정에 따라 공유 옵션은 다음과 같이 제공될 수 있다.

| 공유 범위 | 누가 방문할 수 있나 | 조건 |
|---|---|---|
| 소유자와 워크스페이스 관리자 | 만든 사람과 워크스페이스 관리자 | 새 사이트의 기본 상태 |
| 선택한 활성 사용자 또는 그룹 | 지정한 사람들 | 지원되는 경우 |
| 워크스페이스의 모든 사람 | 워크스페이스 구성원 전체 | 지원되는 경우 |
| 인터넷의 모든 사람 | 누구나 | 공개 게시가 활성화된 경우에만 |

기억할 구분이 셋 있다.

- **공유는 방문 권한일 뿐 편집 권한이 아니다.** 링크를 받은 사람이 사이트를 고칠 수는
  없다.
- **제한 공유에서는 방문자가 접근 권한을 받은 계정으로 로그인해야 한다.** 공개 사이트는
  ChatGPT 워크스페이스 접근 없이도 열린다.
- **사이트의 대상 설정과 사이트 안에 넣은 로그인 기능은 별개의 통제 장치다.** 공개
  사이트를 누구나 열게 두면서, 저장된 진행 상황이나 개인화된 화면을 위해 Sign in with
  ChatGPT를 선택적으로 제공할 수도 있다.

Enterprise 워크스페이스에서는 **공개 게시가 기본으로 꺼져 있고 관리자가 켜야 한다.**
그리고 ChatGPT Sites를 쓸 수 있는지 자체도 Enterprise 관리자가 제어한다. Academy
페이지는 관리자가 확인할 항목으로 Sites 활성화 여부, 누가 사이트를 만들고 공유할 수
있는지, 워크스페이스에 어떤 사이트가 있는지, 누가 접근할 수 있는지, 언제 사이트를
없애야 하는지를 든다.

데스크톱 앱에서는 접근을 넓힐 준비가 됐을 때 해당 턴 끝의 **Share** 버튼을 누른다.
워크스페이스 설정에 따라 특정 사람이나 그룹에 공유할 수 있고, 나중에 사이드바의
Sites 페이지로 돌아가 사이트 설정과 접근을 다시 관리할 수 있다.

## 설정에서 관리하는 것들

**Sites** 를 열고 해당 사이트의 설정으로 들어가면 다음을 다룬다.

| 항목 | 무엇을 하나 | 주의점 |
|---|---|---|
| 접근·공유 | 방문 대상을 바꾼다 | 가장 좁은 범위부터 시작한다 |
| 환경 값과 시크릿 | 호스팅 환경의 환경 변수와 비밀 값을 추가·수정·삭제한다 | 비밀 값은 프롬프트, 첨부 파일, 사이트 콘텐츠에 넣지 않는다 |
| 커스텀 도메인 | 이미 보유한 apex 도메인이나 서브도메인을 연결한다 | Sites가 도메인을 등록해 주지는 않는다. 출시 시점 기준 Enterprise 워크스페이스에서는 제공되지 않는다 |
| 분석(analytics) | 순 방문자 수와 페이지뷰, 기간별 추이를 본다 | 현재 Enterprise 워크스페이스가 소유하지 않은 사이트에서 제공된다 |
| 삭제 | 사이트를 영구 삭제한다 | 삭제하면 복구할 수 없다 |

환경 값과 관련해 한 가지 절차를 기억해 두면 좋다. 호스팅 환경 값을 추가·수정·삭제한
뒤에는 **승인된 저장 버전을 다시 배포해 달라고 요청** 해야 다음 배포에 바뀐 설정이
반영된다.

분석은 별도 SDK를 붙이지 않아도 트래픽이 자동으로 기록된다. 총 순 방문자 수와
페이지뷰, 그리고 두 지표의 시간별 추이를 보여 주고, 기간이나 집계 단위를 바꿔 다른
구간을 확인할 수 있다. **More actions** 에서 **Analytics** 를 고르면 된다.

내리는 방법도 두 가지다. 삭제하지 않고 접근만 없애려면 공유 설정에서 자신이나 선택한
사람들로 범위를 좁힌 뒤, 이전 대상이 더는 열 수 없는지 확인한다. 완전히 없애려면
**Sites** 에서 사이트를 찾아 **Delete site** 를 고르고, 사이트 슬러그를 입력한 다음
**Permanently delete** 를 누른다.

## 라이브 데이터에 직접 연결할 수 없다

여기서 많은 사람이 기대와 다른 지점을 만난다. Academy 페이지는 명확하게 적는다.
**Sites는 현재 라이브 데이터에 직접 연결할 수 없다.**

그래서 사이트 정보가 자주 바뀐다면 권장되는 패턴은 **별도의 예약 작업(scheduled
tasks)** 을 두는 것이다. 예약 작업이 일정에 따라 최신 업데이트를 모으고, 사이트에
넣을 갱신된 내용을 준비한다. 문서가 든 예시는 이렇다. 평일 아침마다 승인된 프로젝트
트래커를 검토해 무엇이 바뀌었는지 요약하고, 최신 마일스톤·담당자·리스크를 일정한
형식으로 정리한다. 사람은 그 결과를 검토하고, 필요할 때 사이트를 갱신한다.

```text
[예약 작업]  평일 08:00
     │
     ├─▶ 승인된 트래커 · 메일 · 메시지에서 변경분 수집
     ├─▶ 무엇이 바뀌었는지 요약
     └─▶ 일정한 형식으로 정리한 초안 산출
                    │
                    ▼
           [사람이 검토·승인]
                    │
                    ▼
        [Sites에 반영 요청 → 버전 저장 → 배포]
```

자동으로 사이트를 갱신하게 만들지 않고 **사람의 검토를 사이에 끼우는 것** 이 이 패턴의
요점이다. 사이트는 여러 사람이 보는 결과물이므로, 갱신도 배포와 같은 무게로 다룬다.

<ConceptCard title="사이트와 프로젝트는 다르다">

웹에서 만든 사이트는 그 사이트를 만든 ChatGPT Work 대화가 끝난 뒤에도 Sites 목록에
남는다. 사이트를 시작하려고 로컬 프로젝트나 별도 설정 파일이 필요하지도 않다. 공식
문서는 **사이트는 ChatGPT의 프로젝트(project)와 별개** 라고 명시한다. 프로젝트는 관련
대화·파일·지침을 묶어 두는 작업 공간이고, 사이트는 호스팅되는 결과물이다.

</ConceptCard>

## 해보기

**배포 전 검토용 버전만 저장하기**

```text
@Sites 지금까지 변경한 내용으로 검토용 버전을 저장해 주세요. 배포는 하지 마세요.
저장된 버전에 무엇이 들어 있는지 요약해 주세요.
공개하면 곤란한 정보, 비밀 값, 공유 권한이 없는 외부 콘텐츠가 있으면 표시해 주세요.
```

**배포하고 방문자 관점 점검 목록 받기**

```text
@Sites 이 사이트를 배포하고 URL을 알려 주세요.
그리고 의도한 방문자 관점에서 확인해야 할 항목을 체크리스트로 정리해 주세요.
로그인 동작과 접근 범위 확인 항목도 포함해 주세요.
```

**접근 범위 변경하기**

```text
@Sites 먼저 현재 사이트 상태와 URL을 보여 주세요.
확인이 끝나면 접근 범위를 우리 워크스페이스 전체로 변경해 주세요.
```

**최신화용 예약 작업 걸기**

```text
평일 오전 8시마다 승인된 프로젝트 트래커를 검토해 주세요.
무엇이 바뀌었는지 요약하고, 최신 마일스톤·담당자·리스크를 같은 형식으로 정리해 주세요.
결과는 제가 검토할 초안으로만 주고, 사이트를 자동으로 갱신하지는 마세요.
```

## 흔한 실수

| 실수 | 무슨 일이 생기나 | 대신 이렇게 |
|---|---|---|
| 확인 없이 바로 배포한다 | 배포 URL은 곧 프로덕션이다. 준비 안 된 내용이 공개된다 | 버전을 저장해 검토한 뒤 배포한다 |
| 내장 브라우저로만 확인한다 | 작업 중 미리보기에는 쓸 수 있지만, 배포된 사이트 확인에는 현재 지원되지 않는다 | 배포 링크를 Chrome에서 열어 확인한다 |
| 처음부터 인터넷 공개로 설정한다 | 되돌려도 이미 링크가 돌아다닌다 | 가장 좁은 범위에서 시작해 필요한 만큼 넓힌다 |
| 비밀 값을 프롬프트나 사이트 콘텐츠에 넣는다 | 사이트 내용과 대화에 남는다 | 사이트 설정의 환경 값·시크릿에 넣는다 |
| 환경 값만 바꾸고 끝낸다 | 이전 배포는 옛 설정을 그대로 쓴다 | 승인된 저장 버전을 다시 배포해 달라고 요청한다 |
| 사이트가 사내 데이터와 실시간 동기화될 것으로 기대한다 | 정보가 낡은 채 방치된다 | 예약 작업으로 갱신 초안을 준비하고 검토 후 반영한다 |

기능 노출은 플랜, 플랫폼, 지역, 롤아웃, 워크스페이스 설정에 따라 달라진다. 특히 Sites는
베타 사용량 한도와 Enterprise 관리자 설정의 영향을 함께 받으므로, 위 화면과 옵션이 그대로
보이지 않을 수 있다.

## 정리

- 게시는 **버전 저장** 과 **버전 배포** 두 단계다. 배포 URL은 모두 프로덕션이므로 검토가
  끝나기 전에는 저장만 한다.
- 배포된 링크는 Chrome에서 한 번 더 열어 확인한다. 작업 중 미리보기와 달리 배포된 사이트
  확인에는 내장 브라우저가 현재 지원되지 않는다.
- 새 사이트는 소유자와 워크스페이스 관리자에게만 열려 있다. 의도한 대상에 맞는 가장 좁은
  범위를 고른다. 공유는 방문 권한이고 편집 권한이 아니다.
- 사이트 설정에서 접근, 환경 값과 시크릿, 커스텀 도메인, 분석, 삭제를 관리한다. 환경 값을
  바꿨으면 승인된 버전을 다시 배포한다.
- Sites는 라이브 데이터에 직접 연결할 수 없다. 예약 작업으로 갱신 초안을 준비하고, 사람이
  검토한 뒤 사이트를 갱신하는 패턴을 쓴다.

다음 섹션에서는 이런 결과물을 만들고 공유하기 전에 반드시 이해해야 하는 권한·승인 모델과
데이터 보호, 그리고 검증 루틴을 다룬다.
