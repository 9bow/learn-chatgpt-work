## 왜 실행 시점까지 넘기나

스킬을 만들면 "어떻게"가 고정된다. 그런데 매주 월요일 아침에 그 스킬을 부르는 일은
아직 내가 기억해야 한다. 월요일에 휴가면 건너뛰고, 바쁜 주에는 수요일에 몰아서 한다.

예약 작업(scheduled tasks)은 그 실행 시점을 넘긴다. 용어집의 정의는 "ChatGPT가
미래 시점이나 반복 일정에 실행하는 프롬프트로, 자체 설정과 실행 기록을 가진다"다.
2026년 7월 첫째 주 릴리스 노트는 예약 작업이 내가 자리에 없을 때도 일을 진행시키는
네 가지 방식을 이렇게 정리한다.

| 실행 방식 | 언제 쓰나 |
|---|---|
| 한 번 실행(run once) | 지금이 아니라 특정 시점에 한 번만 해야 하는 일 |
| 일정에 따라(on a schedule) | 매주 월요일 아침 보고처럼 주기가 정해진 일 |
| 이벤트가 발생할 때(when an event occurs) | 무언가 일어난 다음에 시작해야 하는 일 |
| 변화를 감시하면서(while monitoring for changes) | 바뀌는지 계속 지켜보다가 알려 줘야 하는 일 |

## 두 가지 예약 작업

같은 '예약'이라도 결과가 어디로 돌아오는지에 따라 두 종류로 나뉜다. 이 선택이
실무에서 가장 중요하다.

**독립 예약 작업(standalone scheduled task)** 은 실행마다 **새 대화를 시작**하고
결과를 예약 목록에 보고한다. 용어집은 이 유형의 결과가 **Triage** 에 보고된다고
설명한다. 각 실행이 서로 독립적이어야 할 때, 또는 하나의 예약 작업이 여러
프로젝트를 걸쳐 돌아야 할 때 쓴다.

**대화 안 예약 작업(scheduled task in a chat)** 은 기존 대화의 맥락을 그대로 쓰고,
실행 결과를 **그 대화로 되돌려 준다**. 매번 새 프롬프트로 시작하지 않는다. 용어집은
같은 대화로 돌아오는 반복 예약 작업을 **하트비트(heartbeat)** 라고 부른다.

```text
독립 예약 작업                    대화 안 예약 작업 (하트비트)
─────────────                    ──────────────────────────
저장된 프롬프트                   기존 대화 + 그 맥락
      │                                  │
   ┌──▼──┐  ┌─────┐  ┌─────┐        ┌────▼─────┐
   │새 대화│  │새 대화│  │새 대화│        │  같은 대화 │◀─┐
   └──┬──┘  └──┬──┘  └──┬──┘        └────┬─────┘  │
      │        │        │                 │        │
      └────────┴────────┘                 └────────┘
              ▼                        정해진 주기로 되돌아옴
        Triage / 예약 목록
```

| 기준 | 독립 예약 작업 | 대화 안 예약 작업 |
|---|---|---|
| 맥락 | 매번 저장된 프롬프트에서 시작 | 기존 대화의 맥락을 이어 씀 |
| 결과 위치 | 예약 목록의 별도 실행 기록 | 원래 대화 안 |
| 주기 | 사용자 지정 일정 | 분 단위 간격, 일간, 주간 |
| 어울리는 일 | 주간 정기 보고, 여러 프로젝트 점검 | 오래 걸리는 작업 완료 확인, 검토 루프 유지 |

대화 안 예약 작업이 특히 잘 맞는 상황은 공식 문서가 다섯 가지로 정리한다.
오래 걸리는 작업이 끝날 때까지 확인하기, 결과가 같은 대화에 남아야 하는 연결
출처 폴링, 정해진 주기로 검토 루프를 계속하라고 상기시키기, 플러그인을 쓰는
스킬 기반 워크플로 돌리기, 진행 중인 리서치나 분류 대화를 맥락을 잃지 않고
이어 가기다.

## 로컬이냐 클라우드냐

이 선택을 잘못하면 예약 작업이 조용히 실행되지 않는다.

데스크톱 앱의 예약 작업이 로컬 프로젝트를 쓰면, **예정된 시각에 컴퓨터가 켜져
있고 앱이 실행 중이어야** 한다. 선택한 프로젝트도 디스크에 그대로 있어야 한다.
노트북을 닫고 퇴근하면 새벽 예약은 돌지 않는다.

그래서 공식 문서는 **클라우드(Cloud)** 를 권한다. 웹이나 시간이 지남에 따라
웹사이트를 조사하거나 확인하는 예약 작업에 클라우드가 유용한 이유는, **실행이
내 컴퓨터가 깨어 있는지에 의존하지 않기 때문**이다. 데스크톱 앱 작성창의
**Work locally** 컨트롤을 열어 **Cloud** 가 보이면 그것을 고르면 된다.

```text
                   예약 작업이 필요한 자료는?
                            │
        ┌───────────────────┴───────────────────┐
        │                                       │
  내 컴퓨터의 파일·앱                    웹·연결된 도구·업로드 자료
        │                                       │
   Work locally                              Cloud
        │                                       │
  컴퓨터 켜 두고                          컴퓨터 상태와 무관하게
  앱 실행 유지 필요                       실행됨
```

웹의 ChatGPT Work에서 만든 예약 작업은 업로드한 맥락과 연결된 도구를 쓸 수 있지만,
**내 컴퓨터의 폴더에서 직접 작업할 수는 없다.** 실행 사이에 로컬 폴더가 유지되지도
않는다. 그래서 지속적으로 필요한 지시는 작업 프롬프트나 첨부한 스킬에 넣고, 필요한
원자료는 접근 가능한 프로젝트·업로드·연결된 서비스에 두어야 한다.

## 만드는 방법과 공식 예시

예약 작업은 대화에서 말로 만들 수 있다. 무슨 일을 할지, 일정은 어떻게 되는지,
각 실행이 현재 대화로 돌아올지 새 대화를 시작할지 설명하면 ChatGPT가 프롬프트를
초안 잡고, 알맞은 목적지를 고르고, 범위나 주기가 바뀌면 예약 작업을 갱신한다.

공식 문서의 정기 업데이트 예시 프롬프트를 한국어로 옮기면 다음과 같다.

```text
매주 월요일 아침, [프로젝트명] 에 대해 @Slack 과 @Google Drive 의 새 업데이트를
검토해 주세요. 결정 사항, 막힌 일, 담당자, 미결 질문으로 회의 안건을 갱신해 주세요.
공유하기 전에 초안을 저에게 보내 주세요.
```

  caption="같은 프롬프트가 매주 같은 형식의 회의 안건으로 돌아온다"

변화를 감시하는 형태의 예시다.

```text
매일 오전 9시에 [경쟁사명] 의 [대상 페이지 URL] 을 확인해 주세요.
지난 실행 때와 달라진 부분이 있으면 무엇이 어떻게 바뀌었는지 정리해 주세요.
달라진 게 없으면 "변경 없음" 한 줄만 보고하고 끝내 주세요.
가격이나 플랜 구성이 바뀐 경우에만 저에게 알림을 남겨 주세요.
```

마지막 두 줄이 이 프롬프트의 핵심이다. **보고할 것이 있는지 판단하는 기준**을
넣지 않으면, 매일 "특별한 변화 없습니다"라는 알림이 쌓여서 곧 아무도 읽지 않게 된다.

## 예약 작업과 스킬을 함께 쓰기

예약 작업을 유지 관리하고 팀과 공유하기 쉽게 만드는 공식 권고는 **스킬로 동작을
정의하고, 스킬이 도구와 맥락을 제공하게 하는 것**이다. 예약 작업 프롬프트에는
"무엇을 언제"만 남기고, "어떻게"는 스킬에 둔다.

```text
매주 금요일 오후 4시에 @[주간보고 스킬 이름] 을 실행해 주세요.
대상 프로젝트는 [프로젝트명] 이고, 집계 기간은 지난 7일입니다.
결과 초안을 이 대화로 되돌려 주고, 자동으로 어디에도 공유하지 마세요.
스킬의 완료 전 점검 항목을 통과하지 못한 항목은 따로 표시해 주세요.
```

자동 도구 선택에 의존해서는 안 되는 워크플로라면, 작업 프롬프트에서 특정 스킬을
명시적으로 고르거나 호출하세요.

<ConceptCard title="예약 작업은 사람 없이 돈다 — 권한을 좁히세요">
예약 작업은 **감독 없이(unattended)** 내 기본 샌드박스 설정으로 실행된다. 그래서
권한 설정이 평소보다 더 중요하다. 공식 지침은 작업이 성공하는 데 필요한 가장 좁은
접근으로 시작하고, 네트워크나 더 넓은 파일 접근은 필요할 때만 허용하라고 권한다.

특히 **full access(전체 접근)** 샌드박스에서 도는 백그라운드 예약 작업은 위험이
높다. ChatGPT가 묻지 않고 파일을 바꾸고 명령을 실행하고 네트워크에 접근할 수 있기
때문이다. 관리형 환경이라면 관리자가 관리 요건으로 이런 동작을 제한할 수 있다.
</ConceptCard>

## 예약 전에 반드시 할 일

공식 문서가 반복해서 강조하는 절차가 있다. **예약하기 전에 일반 대화에서 프롬프트를
직접 테스트하는 것**이다. 이 단계에서 세 가지를 확인한다.

1. 프롬프트가 명확하고 범위가 제대로 잡혔는가.
2. 선택한(또는 기본) 모델·추론 강도·도구가 예상대로 동작하는가.
3. 나온 결과가 검토 가능한 형태인가.

예약을 시작한 뒤에도 처음 몇 번의 결과를 검토하고, 결과가 너무 광범위하거나 맥락이
더 필요하면 프롬프트·도구·주기를 조정한다.

## 주의점

- **로컬 예약 작업은 컴퓨터가 꺼지면 안 돈다.** 야간·주말 실행이 필요하면 클라우드를 고르세요.
- **알림 피로를 설계로 막으세요.** "보고할 것이 있는지 판단하는 기준"과 "없으면
  한 줄로 끝내라"를 프롬프트에 넣는다.
- **실행 기록은 쌓인다.** 일괄 동작으로 정리하고, 필요 없는 실행은 보관한다.
- **모델 은퇴 일정을 확인하세요.** 공식 문서는 ChatGPT 로그인으로 `gpt-5.4` 또는
  `gpt-5.4-mini` 를 쓰는 예약 작업은 2026년 8월 31일 은퇴 전에 갱신하라고 안내한다.
  `gpt-5.4` 는 `gpt-5.6-terra` 로, `gpt-5.4-mini` 는 `gpt-5.6-luna` 로 바꾼다.
- **가용성이 다르다.** 기능은 플랜·플랫폼·지역·롤아웃·워크스페이스 설정에 따라
  다르다. 예약 관리 화면은 웹과 데스크톱 앱에서 제공되며, Codex CLI와 IDE 확장에는
  없다. 워크스페이스에서 예약 작업이 켜져 있어야 만들 수 있다.

<ConceptCard title="정교한 주기가 필요하면">
기본 주기 선택으로 부족하면 사용자 지정 일정 컨트롤을 쓴다. 더 정교한 일정이
필요하면 RFC 5545 반복 규칙(RRULE)을 직접 편집할 수도 있다. 예를 들어
`RRULE:FREQ=MONTHLY;BYMONTHDAY=1;BYHOUR=9;BYMINUTE=0` 은 매월 1일 오전 9시를
뜻한다. 비개발 직군이라면 여기까지 필요할 일은 드물고, "월 1회 특정 날짜" 같은
주기가 필요할 때 이런 방법이 있다는 것만 알아 두면 된다.
</ConceptCard>

## 정리

- 예약 작업은 한 번, 일정에 따라, 이벤트 발생 시, 변화 감시 중의 네 방식으로 돈다.
- 독립 예약 작업은 실행마다 새 대화를 시작하고, 대화 안 예약 작업은 같은 대화로 돌아온다.
- Scheduled 화면이 받은편지함 역할을 하고, 실행 기록은 일괄 동작으로 정리한다.
- 컴퓨터 상태에 의존하지 않아야 하면 클라우드를 고른다.
- 예약 전에 일반 대화에서 프롬프트를 테스트하고, 처음 몇 번의 결과를 검토한다.

여기까지는 나를 위한 자동화다. 다음 챕터에서는 한 사람이 만들어 팀 전체가 쓰는
워크스페이스 에이전트(workspace agents)를 다룬다.
